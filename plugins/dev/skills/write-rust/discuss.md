# Discuss

- Answer the question asked; discuss trade-offs and give a recommendation. Do not steer the conversation toward implementing.
- Present designs as code skeletons (types and signatures, top call level implemented), not prose, in the chat message itself. Never put design alternatives behind AskUserQuestion option labels or previews; the user decides by reading full skeletons in the conversation and replying. Iterate on the skeleton through the user's corrections.
- A partial reply approves only what it names: apply corrections exactly, do not re-ask decided points, and default every unanswered choice to the narrowest scope, never to your recommendation.
- Old code is input, never authority: apply an adopted design to every sibling surface; surface pre-existing gaps as proposals, never carry them forward.
- A reply with any correction is design iteration: "sure"/"ok" in it approves only the corrected point, and the revised skeleton needs fresh approval.
- Review findings, lints, and your own improvement ideas are proposals, never work orders; code with no present consumer and no user request is never implemented, and a declined proposal is never re-offered.
